=== TODO, BUGS, ETC ===

DESIGN: function purges are determined automatically by two Ghidra Analyzers modelled
on Ghidra's own X86FunctionPurgeAnalyzer: H8FunctionPurgeAnalyzer covers PRTD/RTD
(variable, immediate-encoded purge sizes), and H8ExtraPopAnalyzer covers the
fixed-size RTS(2)/PRTS(4)/RTE(6) returns via func.setStackPurgeSize(). Note this does
not eliminate the spacebase warning quirk below -- extrapop being correctly resolved
and the decompiler's stack-pointer solver tracking the spacebase fully are two
separate mechanisms; see the quirk below for why the warning still fires even with
purge sizes fully determined.

QUIRK (understood, accepted, not fixing): the decompiler prints "unable to track
spacebase fully for stack" on functions that use @-SP/@SP+ (predec/postinc) stack
addressing -- e.g. isr_sci1_eri. Not an extrapop bug and not a missing DP/EP spacebase
declaration (we deliberately don't model DP/EP as spacebase registers -- see the
x86-segment precedent, can't have two spacebase regs writing into the same ram space).

Root cause is in Ghidra's own StackSolver (coreaction.cc, ActionStackPtrFlow::
analyzeExtraPop): it only recognises SP-derived varnodes defined via INT_ADD, COPY,
INDIRECT, MULTIEQUAL, or INT_AND. Our eab_predec/eab_postinc constructors for @-SP/@SP+
do `SP = SP - 1` (fine) then export a `ptr24` local built via our own spSegment()
userop (a CALLOTHER) -- which isn't one of the five recognised shapes, so the solver
can't solve for it and prints the warning. This is inherent to layering a custom
segment userop on a plain SP stackpointer for 24-bit addressing; not a Ghidra defect
worth reporting upstream, just a narrow analyzer meeting an addressing model it wasn't
built for. Treated as cosmetic unless a specific function's decompiled *output* (not
just the warning) is shown to be wrong.

This may be partially responsible for the decompiler having difficulty assigning local
variables, though that hasn't been confirmed as a downstream effect yet.

Maybe consider making all general registers 24-bit (or giving them access to a 24-bit
extension) with copies of DP/EP/TP in the high byte. CORRECTION: FP/SP are NOT actually widened registers either -- `define register` still declares
R0-R5/FP/SP as plain size=2 (16-bit). SP24/FP24 are separate size=4 pseudo-registers,
and for every other Rn the "24-bit" value is just a `local addr`/`local ptr24` computed
fresh at each addressing-mode use site (via `(zext(DP)<<16)|zext(Rn)` or spSegment()),
not persistent register state. So this idea would be new work across the board, not an
extension of an existing FP/SP pattern -- and per the spacebase quirk above, doing it via
a userop like spSegment() is exactly what keeps the decompiler's stack-pointer solver
from tracking these varnodes, so a real 24-bit-register approach would need to avoid
CALLOTHER if it's meant to also fix that warning. Maybe this will make it easier for
the decompiler to understand pointers, etc. Though it will probably make it harder to
do 32-bit maths, such as MULXU where the result is in R0:R1.

STOP -- before attempting broad widening, read this: this was already tried and hit a
hard Ghidra platform ceiling, not just left undone. Two separate one-per-address-space
limits are already maxed out:
  1. <segmentop> -- Ghidra allows only ONE per address space. This is *why* spSegment()
     exists as a single shared userop for TP-banked registers (FP/SP push-pop, R4-R7)
     instead of each bank register getting its own inline widening.
  2. constresolve (context resolution) -- also one-per-space, and TP already holds that
     slot. EP banking was actually built, wired up, and confirmed stable, but delivers
     NO decompiler benefit for dynamic EP values because of this -- proven dead end,
     not an oversight.
Widening DP/EP the way SP/FP were partially done would hit the exact same ceiling that
already made EP banking a no-op. This is a hard platform limit, confirmed by testing,
not unclaimed work -- don't re-attempt "widen everything" without a new mechanism that
gets around limits 1 and 2 above. The only narrower, still-open option is reworking
just the SP/FP push-pop path to avoid spSegment()'s CALLOTHER shape (e.g. inline
arithmetic like R0-R3 already use) purely to fix the spacebase solver warning above --
that's a real tradeoff (lose segment-aware pointer typing for SP/FP) and does NOT
touch DP/EP's separately-confirmed limitation at all.

Also maybe consider padding all 24-bit things to 32-bit.

Some preserved (unaffected) registers are still showing in the decompilation as being
manually stored and restored.

MOV:G.B #xx:16,<EAd> makes little sense, moving a 16-bit immediate into an 8-bit
register. It does disassemble in IDA, but the only time I encountered the instruction

=== General notes on H8/500 ===

=== Addressing modes ===
Sz: 1=word
    0=byte
 r: 0~7 = use R0~R7 register
Register Direct
  Rn		1 0 1 0 Sz r r r 	EA = Rn
Register Indirect
  @Rn		1 1 0 1 Sz r r r 	EA = 0:15  Rn
                                     16:23 DP/TP/EP
Register Indirect with Displacement
  @(d:8,Rn)	1 1 1 0 Sz r r r	EA = 0:15  (Rn + sign-extended displacement)
                                     16:23 DP/TP/EP
  @(d:16,Rn)	1 1 1 1 Sz r r r	EA = 0:15  (Rn + displacement)
                                     16:23 DP/TP/EP
Register Indirect with Pre/Post-Decrement
  @-Rn		1 0 1 1 Sz r r r    EA = 0:15  (Rn - (1 or 2, based on Sz))
                                     16:23 DP/TP/EP (ignored in Minimum mode)
  @Rn+		1 1 0 0 Sz r r r    EA = 0:15  Rn
                                     16:23 DP/TP/EP (ignored in Minimum mode)
Immediate
  #xx:8		0 0 0 0 0 1 0 0 	1-byte immediate
  #xx:16	0 0 0 0 1 1 0 0		2-byte immediate
Absolute
  @aa:8		0 0 0 0 Sz 1 0 1 	EA = 0:7   EA extension data
                                             8:15  BR
									 16:23 0x00
  @aa:16	0 0 0 1 Sz 1 0 1	EA = 0:15  EA extension data
                                             16:23 DP
PC-Relative
  disp		No EA field. Specified in op-code.
      :8                        	EA = 0:15  (PC + sign-extended displacement)
	                                     16:23 CP
      :16                       	EA = 0:15  (PC + displacement)
	                                     16:23 CP

Where a choice between DP/TP/EP is available, the choice is automatically determined by the choice of general register Rn. For R0~R3, DP is used. For R4~R5, EP is used. For R6~R6 (SP,BP), TP is used.

=== H8/520 and H8/538F variant bugs (found during H8/539F development) ===

--- h8520.pspec ---

NOTE: The <context_data> block sets CP, DP, TP, EP, BR, FPH all to zero as static
global defaults. This is adequate for single-page ROMs but will misidentify
cross-page far calls in any multi-page H8/520 application. The H8/539F setup script
approach (setting context registers per address range at import time) is more correct
for paged ROMs.

--- h8538f.pspec ---

BUG: <data_space space="ram" /> declaration is missing. The H8/520 pspec and the
H8/539F pspec both have this. Without it Ghidra may not correctly identify the data
address space for the H8/538F language.

BUG: The RAM block is defined as initialized="true" with length 0xF000 starting at
0x0000. This covers code space, not just RAM. The block should be uninitialised and
sized to actual on-chip RAM only. Verify against H8/538 hardware manual section 2.

MISSING: No peripheral register symbols at all. The H8/538 shares the same peripheral
set as the H8/539F (SCI, ADC, ports, timers, interrupt controller, DTC, WDT,
multiplier) at the same I/O addresses. The full register map from h8539f.pspec can be
ported to h8538f.pspec directly, with the exception of the flash memory control
registers (FLMCR, FLM_EBR1, FLM_EBR2, FLMER, FLMSR) which are 539F-specific --
the 538 uses EPROM, not flash.
