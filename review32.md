# Session 32 (2026-11-06): the return-address stores in the decompile come from `purge + stackshift` counting the return address twice; a `stackshift="0"` cspec change fixes them

"Verified" = observed on the copy `/RVR_1998_x3 4g63t 21000011 md352553.hex.1` (version 3, language H8:BE:32:H8539F, 741 functions, 355 of them with calls, 1614 call sites) with read-only scripts, or with temporary changes that were rolled back and checked (every purge restored, 0 mismatches). "Unverified" = inference.
Follows the 2026-11-03 handover (session 31) in `todo.md`; supersedes its "Interpretation (NOT verified)" for the stores and its step 0, and withdraws the conclusion of experiment 2 ("stackshift is not the lever").
Nothing was committed, deployed or saved; the cspec, the analyzers and the jar are untouched.

## Summary

1. The decompiler applies, for a callee whose stack purge is known, **extrapop = purge + model.stackshift** (Ghidra `FunctionPrototype.grabFromFunction`; the model's own extrapop is used only when the purge is unknown). The H8 analyzers store the whole pop of the return instruction as the purge (`prts` 4, `rts` 2), which already contains the return address. Every H8 prototype also has `stackshift` 2 (`far*`, `__stdcall*`) or 4 (`__stdcall_ns*`), so the return address is counted twice: after each `pjsr` call the decompiler's SP is raised by `purge + stackshift - 4` (+4 for `_ns`, +2 for the far models; +4 for a near `_ns` callee called with `bsr`).
2. That rise is the drift behind the `uStackNNNN = <return address>` stores (session 31, item 0). The drift accumulates down a function, which is why experiment 2 (stores per callee group 44.1 / 40.0 / 35.8 per 100 sites for stackshift 0 / 2 / 4) looked flat: a store at a call reflects the sum of all earlier callees' drift, not the stackshift of its own callee.
3. A temporary simulation of the fix (extrapop = analyzer purge) takes the call sites with a surviving return-address store from 353 to 23; the 23 left are fully explained (near-return `_ns` callees that the simulation could not reach). The real fix is `stackshift="0"` on every prototype used with an analyzer-set purge; no analyzer or jar change is needed for the stores.
4. The phantom stack argument is NOT explained by this drift (the stack-origin argument count did not improve); it needs its own test.
