16-bit stack pointer that needs to be widened into a larger ram address space. The naive fix — manually building the full address with zext(SP) | (zext(TP) << 16) in SLEIGH, which is exactly what your Rn_banked/SP24 macros do — causes exactly the symptom you're seeing: the raw, unwidened register shows up as unaff_SP/unaff_SS in the decompiler because Ghidra's stack-frame analyzer doesn't recognize "register OR'd with a shifted page value" as "the stack pointer, just wider." It only recognizes a very specific pattern (the exact <stackpointer> register being incremented/decremented and used directly), not a derived recombination.
The actual fix other developers landed on: use SLEIGH's segmentop mechanism in the .pspec, not manual zext/shift/OR arithmetic. That's the same construct Ghidra's own x86 real-mode/segmented modules use for DS:offset-style addressing. One person in that discussion confirmed: "using the segmentop in the pspec was the way to go... had to set the type to protected in order for the segmentation to be correct." This lets Ghidra's decompiler treat the widened address as a proper segment:offset pair it knows how to unwind back to the plain stack pointer, instead of an opaque OR'd value.
What this means for your codebase:

This isn't a quick one-line fix — it's a structural change: define a <segmentop> in h8539f.pspec for the TP/page-to-ram widening (the same mechanism used for DP/EP banking too, which likely has the same underlying issue), and replace the manual (zext(TP)<<16)|zext(SP) pattern everywhere with the segment operator.
This would affect not just SP/FP banking but potentially your DP/EP banked addressing too, since they follow the identical pattern.
