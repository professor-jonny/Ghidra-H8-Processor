=========================================================================
PURPOSE
=========================================================================
The EvoScan MUT logging profile was adapted from a stock Evo 5/6 profile by
updating RAM addresses to match this ROM, WITHOUT independently confirming
that each RequestID's claimed meaning (RPM, TPS, Knock, etc.) is correct
for this ECU/firmware. This log tracks what has been independently
verified against the decompiled ROM (via Ghidra) vs. what is still
inherited assumption from the stock profile.

CORE MECHANISM (verified): MUT table lookup is one level of indirection.
adc_sensor_convert_single @ ROM 0x171c3: for RequestID N, reads a 16-bit
RAM address from ROM[0x2fad0 + N*2], floor-clamps it to 0xEE80, and returns
the byte there. The address ARITHMETIC in the inherited profile is
generally correct; what's been in question item-by-item is the SEMANTIC
label (does that RAM cell really hold what the name claims).

KEY RECURRING LESSON: several items turned out to have correct address
arithmetic but a wrong/inherited semantic label (knock_flag, WGDC
first-pass, F17A "RPM"). Don't trust an inherited name - including a
function name from an earlier "confirmed" session - without checking what
actually reads/writes it. A related technique lesson: several writers were
invisible to plain xref lookups because they used computed/bank-prefixed
addressing (e.g. "1eec6" instead of "eec6") - always retry with a bank
prefix before concluding "no writer found."

=========================================================================
CONFIRMED MUT ITEMS (address + semantics both verified)
=========================================================================

TPS (0x17 -> RAM 0xF13D): writer adc_read_sequence_b (0x15689), channel 7,
  written as 16-bit word at 0xF13C/F13D. ~20 consumers gated on throttle
  position (idle readiness, decel fuel cut, ISC enable, TCU shift sched)
  confirm semantics, not just address.

Battery (0x14 -> RAM 0xF13B): same function/pattern as TPS, channel 5,
  word at 0xF13A/F13B.

AirTemp (0x3A -> RAM 0xF117), MAP/Boost (0x38 -> RAM 0xF15F): writer
  adc_read_sequence_main (0x1556d), even-word/odd-byte pattern.

O2 Sensor (0x13 -> RAM 0xF11F): writer adc_read_sequence_main channel 3;
  consumer o2_closed_loop_fuel_trim_compute (0x237a0) reads it directly as
  narrowband O2 input to closed-loop fuel trim.

O2 Sensor 2 (0x3C -> RAM 0xF123): writer adc_read_sequence_main channel 4
  (immediately after channel-3 O2 read); consumer
  o2_sensor2_threshold_flag_update_f226_bit13 (0x22f16) sets/clears bit13
  of the F226 "lambda mode" register.

Knock Sum (0x26 -> RAM 0xF3A3) and Knock Voltage (0x30 -> RAM 0xF15D):
  written by knock/TCU handler (see STRUCTURAL FIX below). Cross-validated
  against the stock Evo 4/5/6 profile (identical formulas).

knock_adc (0x6A -> F3A9): direct per-cylinder ADC-derived knock intensity,
  genuinely raw-ish (piecewise-scaled, clamped).
knock_var (0x6C -> F963): CONFIRMED address, but holds a DERIVED decision
  magnitude, not raw ADC variance.
knock_base (0x6B -> F967): CONFIRMED address, but holds a snapshot of the
  PREVIOUS cycle's retard output (F3AA), not an independent reading.
knock_change (0x6D -> F969): delta between current/previous knock-ADC
  reading - name is accurate.
knock_dynamics (0x6E -> F3B7): persistence/duration counter, resets and
  sets RAM F200 bit0 under sustained knock - name is reasonable.

Octane Level (0x27 -> RAM 0xEEC8/EEC9): this IS the "knock retard"
  mechanism on this ECU (no discrete retard-degrees value exists, same as
  Evo 4/5/6). Chain: knock sum (F3A2/F3A3) -> knock_event_counter_
  update_eec6 (0x251c4, hysteresis vs ROM 0xB3E/0xB40) -> octane_level_
  compute_from_knock_counter (0x252d3, writes EEC8/9). Separate init/
  override path: octane_level_init_or_force_from_gear_table (0x24e80),
  gear-indexed via ROM table 0x2882, caller not yet found. Octane Level is
  what blends the High/Low-Octane ignition maps already in RVR_base.xml -
  "retard" is implicit in that blend, not a standalone scalar.

TargetIdleRPM (0x24 -> RAM 0xF400/F401): writer idle_target_rpm_compute_
  f400 (0x2629b). Coolant-temp-indexed table, A/C flag (F0F8 bit0x20)
  selects table pair, floor clamp + A/C trim offset.

AirVol (0x2C -> RAM 0xF972/F973) and InjPulseWidth (0x29 -> RAM
  0xF970/F971): both written by fuel_pw_and_airvol_compute (0x29fba),
  gated on RAM 0xF17A (now confirmed to be an engine-torque-derived scale
  value, NOT RPM - see OPEN ITEMS #1) vs a ROM threshold. Secondary reset
  function injpw_airvol_reset_on_fuelcut (0x24680) zeroes both under a
  fuel-cut condition (F25A bit0x28).

ISCSteps (0x16 -> RAM 0xEED4/EED5): writer isc_stepper_output_state_
  machine_eed4 (0x26f82), closed-loop idle stepper state machine.

WGDC (0x86 -> RAM 0xF44C/F44D): writer chain wgdc_correction_integrator_
  update (0x18fe0, reads Boost Control Load Offset @0x10e0a + Turbo Boost
  Error Correction/Max Total Upward WGDC Correction tables @0x12a80/
  0x12a72, writes F44A) -> wgdc_output_clamp_f44c (0x19110, clamps to
  F44C/F44D). Relationship to WGDCCorr (0x8B -> F4AD) NOT yet determined -
  likely two stages of the same pipeline.

TCU Shift Torque Cmd Lo/Hi - Per Gear (RVR_base.xml, ROM 0x1328e/0x13296):
  gear-indexed (confirmed via (gear&3)<<1 indexing), read into RAM
  0xF39E/F3A0, then used as a raw SCI3 protocol command byte sent to the
  TCU (ANDed as bitmask, then passed to an SCI3 TX helper) - NEVER used
  arithmetically. Existing uint16 "units" scaling is correct; small values
  (1-2) are expected, not a data error.

Coolant Temp (0x07 -> RAM 0xF109) / CoolantTempScaled (0x10 -> RAM
  0xF10F): address arithmetic only, NOT independently traced this project.
  See OPEN ITEMS - a fourth, different, independently-traced coolant path
  (F84E->F12E->F130->F29A) also exists and doesn't overlap these addresses;
  unreconciled, do not treat either as authoritative yet.

MAJOR STRUCTURAL FIX: knock + TCU shift torque is ONE function
=========================================================================

What was called "knock_process_main" (0x2933b) and "tcu_shift_torque_mgmt"
(0x28fff) were never two coordinating functions - Ghidra had mis-split ONE
real function into four pieces (tcu_shift_torque_mgmt, FUN_0002910e,
FUN_000292c9, knock_process_main) across a 2-byte inline data literal
(0x186a @ ROM 0x29339-0x2933a) that a disassembly conflict had left
unresolved since session 3. Fixed by marking that literal as data, merging
all four pieces into one function, now named
tcu_shift_torque_and_knock_mgmt (ROM 0x28fff-0x29c32). Fixing the boundary
immediately surfaced its real caller: isr_sci3_eri (COMPUTED_CALL @
0x169b1) - resolving the "knock_process_main has zero xrefs" mystery open
since session 4.

This means the earlier "0xF3AC/0xF3AE - two independently-gated subsystems
intentionally coordinating" framing should be read as "sequential code
within one function" rather than two functions coordinating. The
underlying RAM-register findings below remain correct - only the
two-functions framing was wrong:
  - f3a8/f3aa/f3ac/f3ae/f3b0/f3b2 form a shared "Knock-to-TCU Torque
    Coordination" register cluster, gated by RAM 0xf1f2 bit7
    (gear_config_word_bit7_tcu_knock_coord), itself loaded per-gear via
    current_gear_state_index (RAM 0xf1fc) from gear_config_table_f1f2 (ROM
    0x272). Practical meaning: knock-informed torque-cut coordination with
    the TCU is only enabled in certain gears.
  - The SPECIFIC ROM CALIBRATION TABLE ADDRESSES previously guessed for
    this cluster (108ca/10a24/10a40/10a5c and 125de/12616/1264e and
    125fa/12632/1266a) were REMOVED from the MT-specific XML (see below) -
    never independently traced to a real table read, and several
    physically overlapped Warmup Retard's real byte range. The RAM
    register finding survives; those specific ROM addresses do not.

[SESSION 10, 2026-07-03/04] MAJOR BREAKTHROUGH - RPM MECHANISM ARCHITECTURE
IDENTIFIED VIA H8/538-539 DATASHEET. SEARCH DIRECTION CORRECTED.
=========================================================================

CONTEXT: continuing the RPM-writer hunt after session 9 closed off the
interrupt-vector-table hypothesis (all 17 ISRs checked, none write F17A).
This session took a different approach: consulted the actual H8/538-539
datasheet (grep-able text version at
"datasheets/grep able datasheets/h8538539_text.txt" in the
Ghidra-H8-Processor project folder) instead of continuing to guess from
disassembly alone. This paid off immediately.

[KEY FINDING 1] The chip's timer peripheral is the H8/500-family 16-bit
ITU (Integrated Timer Unit), NOT the TPU/TIOC peripheral the function name
"isr_tpu3_tgi3a" implies. Confirmed by: zero hits for "TIOC" anywhere in
the datasheet, but clean hits for "TOER"/"Timer Output Enable Register"
matching our T5OER register exactly ("enables or disables output of
compare match signals and selects the output level").

[KEY FINDING 2 - THE BREAKTHROUGH] Datasheet section on Timer Mode
Register bit MD3-5:
  "1 Timers 3 and 5 operate in programmed periodic counting mode"
Section 11.8.8 "Programmed Periodic Counting Mode":
  "In programmed periodic counting mode, the value of an externally
  clocked counter is captured into a general register by compare match
  on a different channel. No external input capture signal is needed."
Section 11.8.7 context (channels 2-5 general description):
  "channels 2 to 4 are used for setting the measurement period, and
  channel 5 is used to measure the waveform... If channel 5 is externally
  clocked, the number of external events occurring in regular intervals
  timed by channel 3 can be counted."

CONCLUSION: Channel 3 and Channel 5 are a DATASHEET-DESIGNATED HARDWARE
PAIR for exactly this mode. This explains why the function is named
"isr_tpu3_tgi3a" (fires on channel 3's compare-match/timing event) while
its body manipulates T5xxx registers (channel 5's externally-clocked
counter) - it is NOT a naming error, it's the channel-3 timing-window
interrupt that reads out channel 5's crank-pulse COUNT. This matches
every piece of behavior already traced in isr_tpu3_tgi3a:
  - T5GR2H being WRITTEN with a newly computed value at the end of the
    function = scheduling the next channel-3 window boundary
  - The DAT_0000f9a2/f9a4 -> DAT_0000f9a6/f9a8 buffer rotation = this
    window's captured pulse count shifting into "last window's count"
  - T5OER bit toggling (alternating bit2/bit3) = driving a separate
    dedicated output pin (T5OC1/T5OC2, physical chip pins 64/65 per the
    datasheet's pin table) for a tach/trigger waveform, independent of
    the T5IOC1/T5IOC2 input-capture pins (physical pins 13/14)
  - The sVar3+3 minimum-gap clamp against T5CNTH = glitch-guard ensuring
    the next scheduled window isn't set too close to the current count

[KEY FINDING 3 - CORRECTS SEARCH DIRECTION] Because channel 5 COUNTS
external crank pulses per fixed channel-3 time window (rather than TIMING
THE PERIOD BETWEEN pulses), the RPM value is almost certainly derived by
SCALING A PULSE COUNT (count * constant = RPM), NOT by dividing a period
(period_ticks / constant = RPM). This is the opposite arithmetic
operation from what every previous session (including this one, earlier)
searched for. All previous "check callers of div_u16_sat / div_u32_u16_sat
/ div_u32_u16_rounded" searches (session 2, re-checked session 9) were
looking for the WRONG OPERATION TYPE. 

ACTION FOR NEXT SESSION: search for MULTIPLY operations (mulxu and
similar) applied to consumers of DAT_0000f9a6/DAT_0000f9a8 (the rotated
pulse-count buffer). This is the corrected, datasheet-informed lead
replacing the division-based search. NOT YET DONE THIS SESSION - next
concrete action item.

[SUPPORTING WIRING DIAGRAM EVIDENCE] Cross-checked against the vehicle
harness pinout (RVR_GTA_AIRTREK_space_gear_4cyc_PCM.pdf, uploaded this

[KEY FINDING 1] The chip's timer peripheral is the H8/500-family 16-bit

[KEY FINDING 2 - THE BREAKTHROUGH] Datasheet section on Timer Mode
Register bit MD3-5:
  "1 Timers 3 and 5 operate in programmed periodic counting mode"
Section 11.8.8 "Programmed Periodic Counting Mode":
  "In programmed periodic counting mode, the value of an externally
  clocked counter is captured into a general register by compare match
  on a different channel. No external input capture signal is needed."
Section 11.8.7 context (channels 2-5 general description):
  "channels 2 to 4 are used for setting the measurement period, and
  channel 5 is used to measure the waveform... If channel 5 is externally
  clocked, the number of external events occurring in regular intervals
  timed by channel 3 can be counted."

CONCLUSION: Channel 3 and Channel 5 are a DATASHEET-DESIGNATED HARDWARE
PAIR for exactly this mode. This explains why the function is named
"isr_tpu3_tgi3a" (fires on channel 3's compare-match/timing event) while
its body manipulates T5xxx registers (channel 5's externally-clocked
counter) - it is NOT a naming error, it's the channel-3 timing-window
interrupt that reads out channel 5's crank-pulse COUNT. This matches
every piece of behavior already traced in isr_tpu3_tgi3a:
  - T5GR2H being WRITTEN with a newly computed value at the end of the
    function = scheduling the next channel-3 window boundary
  - The DAT_0000f9a2/f9a4 -> DAT_0000f9a6/f9a8 buffer rotation = this
    window's captured pulse count shifting into "last window's count"
  - T5OER bit toggling (alternating bit2/bit3) = driving a separate
    dedicated output pin (T5OC1/T5OC2, physical chip pins 64/65 per the
    datasheet's pin table) for a tach/trigger waveform, independent of
    the T5IOC1/T5IOC2 input-capture pins (physical pins 13/14)
  - The sVar3+3 minimum-gap clamp against T5CNTH = glitch-guard ensuring
    the next scheduled window isn't set too close to the current count

[KEY FINDING 3 - CORRECTS SEARCH DIRECTION] Because channel 5 COUNTS
external crank pulses per fixed channel-3 time window (rather than TIMING

SCALING A PULSE COUNT (count * constant = RPM), NOT by dividing a period
(period_ticks / constant = RPM). This is the opposite arithmetic
operation from what every previous session (including this one, earlier)
searched for. All previous "check callers of div_u16_sat / div_u32_u16_sat
