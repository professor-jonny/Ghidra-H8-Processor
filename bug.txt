The ConflictBecause special(8) doesn't have an explicit byte offset or sequence enforcement relative to a multi-token pattern, SLEIGH binds it to the current stream parsing position.  When you match map3_page (which consumes byte 1 by matching opcode47=10), SLEIGH shifts its internal parsing context forward by 1 byte.  opcode_special is then parsed correctly from byte 2 because it's listed sequentially after map3_page.  However, if your addrMode2 or eab_direct2 constructors are structured such that addrMode2 fields are directly checked alongside opcode_special without forcing a further progression (or if addrMode2 itself is defined as a plain (8) bit token with no offset), SLEIGH reads addrMode2 fields from that exact same stream offset (byte 2).If opcode_special consumes byte 2 (getting 0x00), and your constructor matches opcode_special=0 & mode2=10 & sz2=0, SLEIGH will try to look for mode2 (bits 4–7) and sz2 (bit 3) in byte 2 (the 0x00 byte), instead of advancing to byte 3!This is why 0xA8 (which selects map3_page on byte 1) fails parsing downstream: byte 2 is being mis-decoded by overlapping tokens rather than stepping through a linear byte sequence.The Clean FixInstead of relying on an empty map3_page subtable or trying to juggle un-offset tokens, you can explicitly map the stream advances. Looking deeper at the shared layout and parsing infrastructure in h8539f.slaspec, there are a few other subtle SLEIGH bugs and architectural pitfalls:1. The P-Code Macro Flag Sync Window (V-Flag Formula Error)In your subflags and subxflags P-code macros:  Code snippetmacro subflags(op1, op2)
{
	result = op1 - op2;
	$(CF) = op1 < op2;
	$(VF) = (op1 s> op2) == (result s< 0);  # <--- HERE
	$(ZF) = result == 0;
	$(NF) = result s< 0;
}
The formula for the signed overflow flag (VF) is buggy. Checking if (op1 s> op2) == (result s< 0) does not correctly flag signed overflow for subtraction.The fix: For a subtraction $A - B = R$, signed overflow occurs if the signs of $A$ and $B$ are different, and the sign of the result $R$ is different from the sign of $A$. In SLEIGH, this is cleanest using the built-in scarry:Code snippet$(VF) = scarry(op1, -op2); 
# Or explicitly tracking sign-bit mismatches:
$(VF) = ((op1 s< 0) != (op2 s< 0)) && ((result s< 0) != (op1 s< 0));

In SLEIGH, attaching multiple positions to the same global token field name symbol _ can cause silent mapping overlap bugs or generation warnings depending on the SLEIGH compiler version.
